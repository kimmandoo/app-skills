# Select on-device face detectors

Select a detector for the product's constraints, not for an assumption that one SDK/model will return identical faces on different platforms. Engine selection is independent of the crop/merge algorithm; use the tiled-face-detection skill if high-resolution group photos need tile passes.

## Prerequisites: make constraints explicit

- Determine whether images and coordinates must remain on device, whether offline *first-run* inference is required, target platform/OS versions, image types (still or video), expected face sizes, app-size budget, minimum acceptable recall/precision, runtime/memory limits, distribution licenses, and whether users can correct omissions.
- Distinguish three different exclusions: **Play-services runtime model download** (bundled ML Kit remains an option); **ML Kit API** (MediaPipe may remain an option); **all Google ML SDK/model code** (exclude both ML Kit and Google ML-backed alternatives). Do not infer the broadest ban from the narrowest one.
- Confirm whether the product needs bounding boxes only or truly needs landmarks, contour, expression, tracking, embedding, or recognition. Do not enable extra work or expose extra personal data without a product use case.

## Compare candidates and decide

1. Inventory image types and existing camera/vision integrations on each target platform. Prefer a local, ready detector consuming those types directly when it meets measured quality. For example, on Android, bundled `com.google.mlkit:face-detection` can consume `Bitmap`/`InputImage` without a runtime model download; on Apple platforms, Vision `VNDetectFaceRectanglesRequest` can consume an upright `CGImage`. A bundled Android model costs app size; Vision behavior can change with OS/revision. These are conditional examples, not a required Android/iOS pair or a requirement to introduce native code into an app whose existing camera stack already handles detection.
2. If ML Kit API alone is forbidden on a target, evaluate MediaPipe Tasks Face Detector and its chosen, pinned still-image model where supported; this is **not** a solution to a blanket Google ML exclusion. If a common model/runtime is needed across targets or all Google ML code is forbidden, consider an independently licensed model such as YuNet with ONNX Runtime, or OpenCV's YuNet detector if its integration cost is acceptable. These are candidates to benchmark, not interchangeable drop-ins or claims of superior accuracy. Cloud APIs violate an on-device-only requirement.
3. Evaluate operational cost alongside quality. A model-backed alternative requires pinned model bytes/version/hash/license, a documented input specification (EXIF orientation, resize/letterbox, channel order, dtype, tensor layout), output decoding, score thresholds/NMS, runtime/delegate choices, update/security handling, and error handling for a missing or incompatible asset. Do not guess tensor values or add a second NMS stage after a high-level API has already postprocessed detections. If a model asset fails to load, surface detector unavailability rather than silently interpreting it as zero faces.
4. Define a narrow detector-to-consumer contract for each target: pass the detector its supported image type and give crop/merge or editing code only validated source-aligned boxes, candidate source (`PREVIEW`/`FULL`/`TILE` if applicable), and small metadata. A native SDK adapter is useful when the chosen stack calls for one; a single-platform app or Flutter pipeline need not create a shared module or copy full pixel buffers to unify SDK calls. Normalize to upright source-image `[left, top, right, bottom]` with a top-left origin: divide pixel x/y by input width/height, or invert y if the detector uses bottom-left normalized coordinates (for Vision, `top=1-maxY`, `bottom=1-minY`). Reject non-finite values, clamp small out-of-range values to `[0, 1]`, then reject non-positive-area boxes. Apply EXIF/upright orientation exactly once; if resizing adds padding, undo it before normalizing to source bounds.
5. Map detector size settings to clearly described *user-level* face-size ranges, not a promise of identical recall or confidence. Calibrate each range on representative inputs: for example, Android ML Kit may accept a minimum input-relative face size, whereas iOS Vision may require post-filtering boxes. If preview and full-resolution passes use different inference modes, document the quality/latency tradeoff. Apply a minimum-face rule in the detector input's coordinates; do not reapply a tile-input threshold after mapping a box to the full source.
6. Adapt the chosen engine's asynchronous behavior: own request status and image lifetime until inference completes, even when app-level cancellation has occurred. Gate late callbacks/task results on current image and operation identity, release native or framework-managed resources when work actually completes, and return a result once. A cancelled call need not stop immediately. Keep an explicit empty-success vs inference-failure distinction, and, when detection suggests editable face/privacy regions, retain manual correction if it fails or misses faces. Do not silently switch to a second detector unless the product explicitly specifies that behavior and tests the expanded state space.

## Diagnostic evaluation and checks

- Prepare a licensed, fixed, annotated still-image set with zero, single, clustered, small, rotated/EXIF, and edge faces plus false-positive-prone scenes. On each target platform/device, record face-size-bucket recall/precision, cold/warm p50/p95 processing time, peak memory, app-size impact, and failure/deadline rate for *each candidate*. Review platform/OS upgrades against the same set. A build passing or identical model filename is not evidence of matching detection quality.
- Feed each detector integration a known upright box and compare source-normalized values: a pixel box `(25, 50, 75, 100)` on a `100 x 200` input and a bottom-left normalized box `(minX=.25, minY=.5, maxX=.75, maxY=.75)` both yield `(left=.25, top=.25, right=.75, bottom=.50)`. Run the representation(s) supported by the target, then repeat with rotated/mirrored EXIF and, if used, resize/letterbox. Confirm all outputs finite, positive-area, in bounds, and mapped exactly once.
- Exercise cancellation, image replacement, model-load failure, SDK exception, and a successful request returning zero faces. Verify no stale consumer update, callback duplication, unreleased image, or conversion of failure into an apparent no-face success. Inspect artifact dependencies and shipping license notices before declaring a bundled or third-party option usable.

## Stop conditions

Do not ship an engine without measured quality on the target photo mix, a reproducible model/SDK and licensing decision, correct orientation/coordinate mapping, bounded image/resource ownership, and acceptable latency, memory, offline availability, and app size. If a policy changes from "no runtime download" to "no Google ML code," redo candidate selection rather than relabeling the existing detector.
