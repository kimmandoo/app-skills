# Local-first event sync

Keep the local materialized view usable offline. Record each edit as a durable event alongside its local state change; synchronize the events rather than replacing the remote current-state document. Treat remote events as untrusted input. For cloud membership, security rules, local-to-cloud cutover, and restore, use [shared-cloud-access](../shared-cloud-access/SKILL.md); this skill owns event validation, push/pull, conflict detection, and local materialization.

## Establish the contract

1. Locate the local event log, materialized entities, remote event store, validation codec, sync coordinator, and conflict UI. Trace actual call sites and tests, not only design notes. Identify which remote adapters are active and which are legacy or export-only; an export artifact is not implicitly a sync source.
2. Define the event envelope used by the consuming protocol: stable unique event ID, collection/entity identity, action type, the author's base version, committed entity version, actor, and a schema-compatible payload. If the protocol includes timestamps, checksums, or an explicit commit marker, specify their serialization, validation, and trust limits. Keep event sync status separate from the entity's displayed state.
3. Make local creation/update/delete atomically persist the new materialized state and a new pending event; never infer that an updated entity was remotely saved merely because its local row changed. For a new entity, start from base version zero and advance to the next version; for edits and tombstones, record the version observed by the author. Preserve pending and failed events until acknowledged or explicitly resolved. Choose a soft-delete/tombstone representation so another client can replay deletion.

## Validate and pull

1. Fetch events for the selected collection; if using a committed-time cursor, apply an overlap/backfill window and deduplicate rather than trusting client clocks or an exact cutoff. Advance the durable cursor only after successfully processing the corresponding remote batch. Support a full replay/recovery path when a cursor or backfill window cannot cover missing events.
2. Before materialization, check collection identity, required fields, supported schema and action types, valid version relationships, and payload shape. When present in the protocol, validate timestamp, commit marker, and checksum over the agreed payload bytes. A syntactically valid event is not automatically a valid transition. Reject incompatible or incomplete records without altering local state; retain a diagnostic reason and do not silently discard remote evidence.
3. Deduplicate by `event_id` both within the fetched batch and against the durable local log. Identical replay is a no-op; a reused ID with different content is corruption, not an edit. Distinct IDs claiming the same entity and version require conflict diagnostics; deterministic time/ID tie-breaking may select a displayed state but must not silently erase evidence of the collision.
4. Apply accepted events and their log entries in a local transaction. Materialize by entity identity and monotonic version; never roll back a newer committed local version because older rows arrive later. Keep pending edits available when a newer remote event supersedes their base version, mark the local edit conflicted, and show the remote state without deleting the proposed local change. Pulling the same batch twice must not create duplicate events, regress versions, or change the displayed state.

## Push and resolve

1. Select pending **and failed** events in stable order; gate write attempts on current access rights as specified by the collection's authority model. A read-only failure must not delete edits. Compare each event's `base_version` to the latest remote version for its entity; a remote version ahead of the base is a conflict. Reject a remote version behind the base as an inconsistent history to investigate, not permission to append out of order.
2. Append with a stable event ID and a server-side conditional/transactional version update: recheck the remote version inside the atomic write, require the exact expected base, advance to the next version, and never create a second remote event when retrying an already accepted ID. Do not claim a preliminary version read prevents a two-client race. When a checksum is used, it detects payload mismatch under the agreed encoding; it does **not** prove atomic publication. Require a transactional version guard, immutable event record, or an equivalent verified commit protocol. Verify an existing ID's content before treating it as acknowledged when the store permits such a check.
3. Mark events synced only after confirmed remote acceptance. On network failure or uncertain acknowledgement, keep the same event ID retryable (`pending` or `failed`); after reconnect, reconcile remote existence/version before retrying. If a batch can partially succeed, acknowledge individual confirmed IDs rather than marking every event failed or synced together. Distinguish quota, authentication, write denial, malformed-event, and conflict outcomes in user-facing status without silently changing local data.
4. For a conflict, preserve the original local event and display both the latest remote state and the unapplied local intent. Let the user keep remote, or explicitly reapply the intent as a **new** event based on the newest remote version; do not silently overwrite and do not silently rewrite the original conflicted event. Recheck access and version again at the final append.

## Verify with disposable two-client data

- **Two clients, same entity:** Both observe a common version, then make different offline edits. Push one, then the other. Assert only the first append advances remote version; the second remains a visible conflict, retains its payload, and can be explicitly reapplied as a new version. Repeat with delete versus update and with a second entity to verify per-entity isolation. Race both pushes to test the remote conditional write, not just the client's preliminary read.
- **Offline and uncertain acknowledgement:** Create an event without connectivity; restart and confirm local state and the pending event persist. Fail an append, reconnect, retry, and assert exactly one remote event and a synced local event. Simulate a remote commit followed by a lost response, then retry the same ID; do not duplicate or lose the edit. Pull the same history twice and test out-of-order events, cursor overlap, and a recovery/full replay.
- **Invalid and competing remote events:** Mix a valid event with missing required fields, incompatible schema, malformed payload/type/version, wrong collection, a duplicate ID with changed payload, and two distinct IDs at one entity version. Also inject an invalid checksum, commit marker, or timestamp when those fields exist in the chosen protocol. Confirm only valid events enter local materialization, invalid records are diagnosed, same-version collisions remain visible, and a replay cannot regress the local view. Exercise a fault between event publication and version update to prove atomicity comes from the storage protocol, not a checksum.

## Evidence limits

Codec validation of required fields, payload shape, and any configured commit marker/checksum supports **record rejection**, not proof of an atomic remote commit. A local event ID check supports replay idempotence, not proof that remote retries are idempotent. A client-side version comparison detects known stale edits, but a concurrent writer can win after that read. Confirm the remote write's version guard, retry semantics, and security configuration independently before declaring the two-client scenario safe. Tests against an in-memory remote demonstrate engine behavior only; pair them with a targeted integration or fault-injection check for the real remote adapter. Do not promote design-only background triggers, diagnostics, or conflict UI into claimed implemented behavior without tracing the live path.
