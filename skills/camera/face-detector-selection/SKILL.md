# Select on-device face detectors

Select a detector for the product's constraints, not for an assumption that one SDK/model will return identical faces on both platforms. Engine selection is independent of the crop/merge algorithm; use the tiled-face-detection skill if high-resolution group photos need tile passes.

## Prerequisites: make constraints explicit

- Determine whether images and coordinates must remain on device, whether offline *first-run* inference is required, target platform/OS versions, image types (still or video), expected face sizes, app-size budget, minimum acceptable recall/precision, runtime/memory limits, distribution licenses, and whether users can correct omissions.
- Distinguish three different exclusions: **Play-services runtime model download** (bundled ML Kit remains an option); **ML Kit API** (MediaPipe may remain an option); **all Google ML SDK/model code** (exclude both ML Kit and Google ML-backed alternatives). Do not infer the broadest ban from the narrowest one.
- Confirm whether the product needs bounding boxes only or truly needs landmarks, contour, expression, tracking, embedding, or recognition. Do not enable extra work or expose extra personal data without a product use case.

## Compare candidates and decide

1. Inventory existing native image types and adapters. Prefer a local, ready detector consuming those types directly when it meets measured quality: for example, Android `com.google.mlkit:face-detection` (bundled, available without a runtime model download) with `Bitmap`/`InputImage`, and Apple's built-in Vision `VNDetectFaceRectanglesRequest` with an upright `CGImage`. A bundled Android model costs app size; Vision behavior can change with OS/revision. Two native inferencers can still share *one* post-inference product contract.
2. If ML Kit API alone is forbidden, evaluate MediaPipe Tasks Face Detector and its chosen, pinned still-image model; this is **not** a solution to a blanket Google ML exclusion. If a model/runtime must be shared or all Google ML code is forbidden, consider an independently licensed model such as YuNet with ONNX Runtime, or OpenCV's YuNet detector if its native bridge cost is acceptable. These are candidates to benchmark, not interchangeable drop-ins or claims of superior accuracy. Cloud APIs violate an on-device-only requirement.
3. Evaluate operational cost alongside quality. A model-backed alternative requires pinned model bytes/version/hash/license, a documented input specification (EXIF orientation, resize/letterbox, channel order, dtype, tensor layout), output decoding, score thresholds/NMS, native bridge/delegate choices, update/security handling, and error handling for a missing or incompatible asset. Do not guess tensor values or add a second NMS stage after a high-level API has already postprocessed detections. If a model asset fails to load, surface detector unavailability rather than silently interpreting it as zero faces.
4. Choose the narrow shared boundary: pass platform-native images into platform adapters; pass only validated source-aligned boxes, candidate source (`PREVIEW`/`FULL`/`TILE` if applicable), and small metadata into shared merge/editor logic. Example: Android top-left pixel box → divide x by input width and y by input height; Vision bottom-left normalized box → `left=minX`, `right=maxX`, `top=1-maxY`, `bottom=1-minY`. Clamp out-of-range values and reject non-finite or zero-area results before sharing. Apply EXIF/upright orientation exactly once. If a resize uses padding, undo it before normalizing to source bounds. Never copy a full pixel buffer into a cross-platform layer only to unify SDK calls.
5. Map SDK size settings to clearly described *user-level* face-size ranges, not a promise of identical recall or confidence. Calibrate each range on representative inputs: Android ML Kit may accept a minimum input-relative face size, whereas iOS Vision may require post-filtering boxes. If preview and full-resolution passes use different inference modes, document the quality/latency tradeoff. Apply a minimum-face rule in the detector input's coordinates; do not reapply a tile-input threshold after mapping a box to the full source.
6. Adapt the chosen engine's asynchronous behavior: own request status and image lifetime until native work completes, even when app-level cancellation has occurred. Gate late callbacks/Swift-task results on current image and operation identity, release native resources on completion, and return a result once. A cancelled native call need not stop immediately. Keep an explicit empty-success vs inference-failure distinction, and retain manual face-region editing if detection fails or misses faces. Do not silently switch to a second detector unless the product explicitly specifies that behavior and tests the expanded state space.

## Diagnostic evaluation and checks

- Prepare a licensed, fixed, annotated still-image set with zero, single, clustered, small, rotated/EXIF, and edge faces plus false-positive-prone scenes. On actual supported Android/iOS devices, record face-size-bucket recall/precision, cold/warm p50/p95 processing time, peak RSS, app-size impact, and failure/deadline rate for *each candidate*. Review platform/OS upgrades against the same set. A build passing or identical model filename is not evidence of matching detection quality.
- Feed each adapter a known upright box and compare source-normalized values: Android pixel `(25, 50, 75, 100)` on a `100 x 200` input and Vision normalized `(minX=.25, minY=.5, maxX=.75, maxY=.75)` both yield `(left=.25, top=.25, right=.75, bottom=.50)`. Repeat with rotated/mirrored EXIF and, if used, resize/letterbox. Confirm all outputs finite, positive-area, in bounds, and mapped exactly once.
- Exercise cancellation, photo replacement, model-load failure, SDK exception, and a successful request returning zero faces. Verify no stale edit, callback duplication, unreleased image, or conversion of failure into an apparent no-face success. Inspect artifact dependencies and shipping license notices before declaring a bundled or third-party option usable.

## Stop conditions

Do not ship an engine without measured quality on the target photo mix, a reproducible model/SDK and licensing decision, correct orientation/coordinate mapping, bounded native resource ownership, and acceptable latency, memory, offline availability, and app size. If a policy changes from "no runtime download" to "no Google ML code," redo candidate selection rather than relabeling the existing detector.
