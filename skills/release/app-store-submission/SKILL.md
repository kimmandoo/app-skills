# App Store submission

## Scope and inputs

Use this for the **App Store Connect console**, not for signing/exporting an IPA or drafting store copy. Start with [release-preflight](../release-preflight/SKILL.md), the verified iOS handoff from [release-artifacts](../release-artifacts/SKILL.md), and version-specific claims/locales from [store-submission-content](../store-submission-content/SKILL.md). For tracking-related review issues, use [att-review](../att-review/SKILL.md). Collect the intended app/bundle ID, platform, version, build number, release choice, target countries or regions, account role, and current app-version **and submission** statuses. Check current App Store Connect requirements and the account's actual permissions before acting; do not infer console access, upload, review, approval, or availability from local artifacts or TestFlight.

## Prepare the version in App Store Connect

1. In **Apps**, use the intended app record and platform; create the record or new platform version if needed. Verify bundle ID, version number, and target distribution against the release handoff. A completed upload must finish processing and become selectable before it can be associated with a version. In the version's **Build** section, select the processed build with the exact intended version/build identity and save. Only one build can be associated with a version at a time; if the selected build is stale or wrong, replace it before submission. An upload or TestFlight test is **not** an App Review submission.
2. Complete the fields actually required for this app/version/account: localized product-page metadata and screenshots matching the selected build, support/privacy URLs, age-rating answers, App Privacy answers reflecting app and SDK data use, rights and content declarations, pricing and country/region availability, and export-compliance questions or documents where applicable. Resolve a selected build's **Missing Compliance** status before submitting. Check applicable In-App Purchases/subscriptions and any associated review items for their own configuration and review readiness. Use the copy skill to author text, not this skill; do not guess current limits or assume all fields apply to every app.
3. Fill **App Review Information** with a reachable contact and test instructions. If sign-in is needed, provide a working, non-expiring demo account in the console's reviewer-access fields, including any required SSO, MFA bypass/test flow, sample data, account permissions, location, hardware, or backend configuration necessary to reproduce the features. Verify access against the selected build without putting credentials in source control or public release notes. Explain unusual flows and any requested review evidence truthfully; do not claim screenshots or tests that have not occurred.
4. Choose and save the version's **App Store Version Release** option: manual release after approval, automatic after approval, or automatic after approval **no earlier than** the selected date/time. For an eligible *version update*, use **Phased Release for Automatic Updates** only when supported and deliberately chosen; this stages automatic updates, **not** manual App Store downloads. Check the actual console choices and account requirements, including any pre-order constraints, before committing to a release plan.

## Send it to App Review

1. Recheck the selected build, version, metadata, reviewer access, declarations, release option, and any other items in the submission. On the version page choose **Add for Review** and select/create the draft submission. **Ready for Review** means it was added to a draft, **not** sent to Apple.
2. Open **Draft Submissions** or **App Review**, verify the draft contents, then separately click **Submit for Review**. Confirm that the submission reaches **Waiting for Review** (Apple received it); **In Review** means review has started. If a validation error blocks submission, resolve the actual field or build problem and retry only after rechecking the draft. Record the observed version/build, submission items, status, chosen release option, and any console confirmation; never invent confirmation or timestamps.

## Decide from the current status

- **Prepare for Submission / Ready for Review:** Finish outstanding fields or build association; if Ready for Review, submit the draft as a separate action. **Waiting for Review / In Review:** Monitor the App Review page, status history, and messages; reply with requested facts and reviewer steps. Some fields cannot be edited after submission; if a replacement build or locked asset must change, follow Apple's remove-from-review flow first, then recheck the new draft rather than assuming an upload silently replaces the reviewed build.
- **Metadata Rejected:** Read Apple's exact issue and guideline, correct the rejected metadata/reviewer information, and reply explaining the change. When only metadata is wrong, the same build can be resubmitted; do not generate a new binary for a metadata-only fix. **Rejected / Invalid Binary:** Diagnose the issue rather than guessing from the label. If app behavior or binary requirements need changing, fix and verify the app, produce/upload a new build with a new build number via the artifact workflow, wait for processing, replace the selected build in the version, and align review notes and declarations before resubmitting. For **Invalid Binary**, Apple requires a build meeting current requirements; select an eligible build or upload a corrected one. Recheck the Build section immediately before sending so the old build is never resubmitted by accident.
- **Submission Unresolved Issues / item Accepted:** Inspect every rejected item on the submission; acceptance of one item does not release it while another is rejected. Edit and **Add for Review** the corrected item, or intentionally remove rejected items that need not ship together; then choose **Resubmit to App Review** from the submission details once all rejected items are addressed. Removed items cannot be re-added to that same submission. **Developer Rejected:** It was removed from review; decide whether the same build is still suitable, refresh the submission details, then submit again when ready.
- **Waiting for Export Compliance / Pending Apple Release:** Check the specific hold and applicable compliance or OS-release requirement; do not claim publication. **Pending Developer Release:** An accepted version still needs an authorized user to choose **Release This Version** and confirm for that platform. With automatic or scheduled release, monitor until the configured conditions and processing finish. **Processing for Distribution / Ready for Distribution:** These do not by themselves prove that the intended version is publicly obtainable in every target region.

## Confirm availability and handoff

After the configured release path, check each intended country's/region's **App Store availability status**, the public listing and localized metadata, and the offered version on an eligible device or storefront. Distinguish **Available** from **Available on App Release**, pre-order, processing, or **Not Available**; investigate agreements, pricing, country restrictions, ratings, or other actual console blockers rather than treating approval as publication. During phased release, monitor its state separately from storefront availability. Record only observed actions, status changes, reviewer replies, selected build and public verification; if console access or live storefront verification is unavailable, leave the outcome explicitly unverified and name the next authorized action.
